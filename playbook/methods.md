# Methods catalogue: techniques that worked

Each entry: what it is, the game it came from, and the pitfall learned. Games: STALKER (Shadow of COOP / Clear COOP on xrMPE), Fallout New Vegas (fnv-coop, NV:MP), Dungeon Keeper 1 (KeeperFX Archon co-op), Ocarina of Time (Shipwright-Online fork), Animal Crossing GameCube (ac-decomp and PC port), Deus Ex (HX revival).

## 1. Research

- **Search for existing attempts before designing anything.** Search GitHub (including forks and non-default branches), ModDB, Nexus, forums, and the game's Discord. From: Animal Crossing, Deus Ex, FNV. Pitfall: the first search said "no co-op exists" for two games that had working co-op (a full multiplayer fork living on a non-default `multiplayer` branch; an old Deus Ex co-op mod last built in 2019). Say "not found by search X" and keep looking at forks, branches, issue trackers and release pages before telling the owner something does not exist.
- **Look at sibling engines and families.** A co-op mod for another game on the same engine, or a multiplayer fork of the same decomp, is often most of the work. From: Dungeon Keeper 2 shared-keeper co-op used as the design model for DK1; sm64coopdx style "puppet" players used as the model for the Animal Crossing PC port. Pitfall: a design that is already in progress upstream (DK1 had "Archon" refactor PRs in flight) means you should read their PRs first and build on the same seams.
- **Use archive.org, ModDB and Nexus for dead mods.** The Wayback Machine for deleted download pages and wikis, ModDB for last-update dates and comments about abandonment, Nexus for mod descriptions and reverse-engineering threads. From: Deus Ex HX (last build 2019, a builds server still online), FNV (a modder had already reverse engineered part of the closed netcode). Pitfall: a forum "re-upload" is a moderator re-posting a link, not a new release. Check the file itself.
- **Read foreign-language docs and chats directly.** Russian forum threads and a German known-bugs file were read in the original and summarized in English; keep error strings untranslated for searching. From: STALKER, Shipwright-Online. Pitfall: machine translation of technical terms is wrong in small ways; quote the original string next to the translation.
- **Mine the mod's chat for bugs.** See [discord-export.md](discord-export.md). Safer routes first (admin export, bot, manual paste).
- **Verify download claims.** Hash and date the file, read the version string inside, and say in the notes which link is official. From: STALKER, where a launcher never updated its displayed version.

## 2. Getting the game and running more than one copy

- **Isolated test install copied from the store install.** Copy the install to a workspace folder, point INIs and saves inside it, never edit the owner's install, saves or config. Back up anything touched. From: Deus Ex, DK1, FNV, STALKER. Pitfall: an agent set an owner INI read-only during an experiment; it had to be reverted. Use instance-local config. A copy at another path does not isolate saves: The Witness keeps them in `%APPDATA%\The Witness` whatever folder the exe runs from, and starting a New Game from the copy rewrote the owner's latest existing campaign save there. Find where the game writes before the first launch, and back up and hash that folder first (From: The Witness). A test copy you didn't make yourself may not be a copy: on Mafia: Definitive Edition, a folder from an earlier session looked like a full 36 GB copy, but 4,843 of its 4,883 files were hard links to the store install, so any write to them would have changed the owner's game. Before trusting a copy, run `fsutil hardlink list <file>` on a few big data files: an isolated file lists only one path. A copy made with `robocopy /E /COPY:DAT` is a real copy (From: Mafia: Definitive Edition).
- **Windowed, minimized, no intro, unfocused-friendly.** Windowed low resolution, "always active" or equivalent, start minimized without taking focus, skip first-run wizards and intro movies in config. From: FNV (800x600 windowed, `bAlwaysActive`), DK1 (cursor capture off, empty startup), Deus Ex (software renderer, because two Direct3D windows fight for exclusive mode), Gothic 3 (the new-game intro video blocks the session loop for 214 s, so no per-frame hook runs; with no config switch found, one Escape posted to the game's own window skipped it every time). Pitfall: full-screen launches made the owner's PC unusable; this was the loudest complaint.
- **Hardlinked instances.** Make N copies of a big install as hardlinks (one set of bytes, separate INI and save files per instance). From: FNV. Pitfall: hardlinks share content, so anything that writes into a hardlinked file changes every instance; keep only config and saves as real copies.
- **Single-instance locks: mutex rename, then FindWindow.** In your own process (a plugin or in-process hook), rename the named mutex per process id, then neutralize the "does a window of my class exist" check, which otherwise makes copy two silently return from `WinMain`. Nucleus Co-op's handler API is a good catalogue of lock types (mutex, event, semaphore, window lookups, shared documents folders, Steam checks). From: FNV. Pitfall: fixing the mutex was not enough; the second copy exited without any message because of the window-class check. Look for every instance check before declaring it fixed. Gothic 3: the exe exits with code 0 while the named mutex `GenomeMutex` exists; the first copy's own plugin closing its handle to it (found by listing the mutant handles of its own process with `NtQueryObject`) was enough, there was no window-class check. Also: killing handles in other processes was refused by the safety layer and by policy; do it only inside your own process. With two pairs of test copies on one PC (two agents), any game may be the one holding the mutex: have every game release its own handle as soon as its test bot answers, and retry a start that exits early after a short random pause (From: Gothic 3). MW2 (2009, 64-bit) has a third kind: a PID file `__iw4sp` in the game folder; copy two quits silently while that PID is a live game. A second folder with its own exe and `players/` and hardlinked data files runs a second copy without any patch.
- **Drive menus through the game's own message queue.** Calling a menu button's handler from a plugin can run the whole next game state inside your call; Gothic 3 stopped updating that way. Focus the button through the GUI API, then post Enter to the game's own window so the game handles it in its normal message pump. This is not OS input: other windows are unaffected and the game does not need focus. From: Gothic 3.
- **Per-instance Steam environment.** Set the app id environment variables and a `steam_appid.txt` so a packed exe does not relaunch through Steam. From: FNV, MW2. Pitfall (MW2 2009, 64-bit): the game deletes `steam_appid.txt` itself during Steam init, so on the next launch SteamStub exited with code 53 and Steam started the owner's real install, which rewrote its `config.cfg`. Set `SteamAppId` and `SteamGameId` on every launch and kill any game process outside the test folder.
- **Two LAN clients on one PC (IP-identified lobbies).** When the LAN code identifies players by IP, two instances on one IP join but break at game start. In your proxy DLL give each instance its own loopback address: report it from `gethostbyname`, bind sockets to it, re-send broadcasts as unicast to the other instances, and switch off `SIO_UDP_CONNRESET`, or the ICMP "port unreachable" from those unicast copies makes the receiver lag until joins time out. From: C&C3 Tiberium Wars. Pitfall: also check the game's own "my IP" setting (C&C3 `GameSpyIPAddress` in Options.ini) and give each instance its own game port.
- **Background instances that still run.** Many games only render and simulate while they are the foreground app. Hook `GetForegroundWindow`/`IsIconic` (report active, not minimized), force `SW_SHOWMINNOACTIVE`, no-op `SetForegroundWindow`/`SetFocus`, answer `GetCursorPos`/`GetAsyncKeyState` from the posted messages and block `SetCursorPos`/`ClipCursor`, and feed posted keys into the DirectInput keyboard. From: C&C3. Pitfall: with an already-hooked `Present` (Steam overlay) vtable patches are bypassed; chain over the existing jump instead.
- **Isolation must cover the store client and other apps, not only the game process.** Redirecting the game's save folders from inside its process (ntdll file hooks) does not stop other processes from writing the real save and settings files. Steam's cloud-save API (`ISteamRemoteStorage`) is serviced by `steam.exe`, which writes every `FileWrite` into `Steam\userdata\<id>\<appid>\remote` even with Steam Cloud switched off for the game; the NVIDIA App rewrote the game's real settings file when it saw the game start. Back up and hash the real save and store folders before the first launch, check them after every run, and block remote-storage writes inside the game process: take the same `ISteamRemoteStorage` the game uses after its `SteamAPI_Init` and replace the write slots in its vtable (read the slot offsets from `steam_api64`'s one-jump flat wrappers, `mov rax,[rcx]; jmp [rax+off]`, and refuse to run if they look different). From: Middle-earth: Shadow of War (16 autosaves in 5 minutes, each also a `FileWrite`). Pitfall: the first session that saved put the test save into the real Steam userdata folder; only the after-run hash check caught it.
- **Offline test copies: fail connections, do not refuse sockets.** Refusing socket creation (`\Device\Afd`) looked like a bug to the game, which showed a server error dialog that needed a human. Failing outbound connect, ConnectEx and UDP sends to non-loopback addresses with "network unreachable" (in an `NtDeviceIoControlFile` hook on AFD requests 0x12007, 0x120C7, 0x12023) looked like an unplugged PC: the game reached the main menu and played, retrying two HTTPS hosts quietly. Loopback stays open for local co-op tests. From: Middle-earth: Shadow of War. Pitfall: the AFD request layouts are undocumented; measure them with a probe on the target Windows build and block anything you cannot parse.
- **A "game slot" lease.** A tiny lock file with owner, TTL and wait, so several agents do not launch the game at once. From: FNV. Pitfall: without it agents killed each other's runs.
- **Hard-link the big read-only files, but start two copies to prove a second process can open them.** One base copy plus hard-linked instance folders cost about 40 MB per instance. The game's 2.7 GB `data-pc.zip` could not be shared: the second instance failed with `error opening bundle file data-pc.zip` and `fatal_error_data_corruption` while the first ran, so that file needs a real copy per instance, unless your mod adds `FILE_SHARE_READ` to that open (the game passes share mode 0 to `CreateFileA`; hooking `CreateFileA`/`W` in the exe's import table fixed it, and two instances then ran, found each other and passed the state check on one shared 2.7 GB file). Keep only the files the game writes (logs, a settings file, your mod DLL and config) private, never write to a hard-linked file in place, and keep a manifest (size, mtime) of the base copy so a game writing through a link is detected. From: The Witness. Pitfall: the failure only shows in the second instance's own log, and a copy that worked alone looks fine.
- **Measure the frame rate of a background game; do not assume.** Measured with the engine's frame counter: 724 fps when the window is the active one (uncapped), about 10 fps whenever it is not the foreground window, minimized or not. (A first measurement said "unfocused runs at full speed"; it was wrong, the window I had sent to the bottom was still the active one.) Posting `WM_ACTIVATEAPP`, `WM_ACTIVATE` and `WM_SETFOCUS` to the window did not stop the throttle; the loop's own two flag bytes did (see the in-process input bullet in section 7: holding them from a `Present` hook gives a background instance at its frame cap). Put a frame cap in your mod (a `Present` hook can sleep out the rest of the frame) so an active instance does not run at 700 fps, start games with `SW_SHOWNOACTIVATE`, and expect the game to grab the foreground anyway while it loads (a small guard that hands the focus back to the previous window stops it interrupting whoever types). From: The Witness.
- **If the game reads raw input, a `SendInput` bot owns the whole desktop.** `RegisterRawInputDevices` input is delivered only to the focused window, so such a bot steals focus from anyone typing and two bots cannot run at once. Serialize them with a desktop-wide lock until input is injected inside the process, and prefer scripted in-game input (the way MDK2's bridge does it) from the start; the in-process input bullet in section 7 shows how it was done for The Witness. Likewise screenshots by screen capture are wrong for covered windows; take them from the back buffer. From: The Witness, MDK2.
- **Windows Firewall asks once per exe path, and a cancelled prompt becomes a Block rule.** Every new per-instance copy is a new path, so the prompt returns on each copy. One elevated script that creates a narrow inbound Allow rule per exact lab exe path, limited to remote address 127.0.0.1, ends the prompts without touching the real installs; an agent cannot click the prompt (it is elevated) and cannot create the rules without one UAC approval from the owner. From: MDK2, The Witness.
- **Several agents need every shared name derived from a lease.** Ports, instance folders, pid files and tool folders hard-coded in scripts collide as soon as two agents run. Give each agent a lease from one slot pool (free-RAM guard, expiry, first-in-first-out) and derive the rest from the slot numbers; take the agent's identity from its git worktree folder name; kill only processes you registered or that run from your own slot folders. From: MDK2 and The Witness, three agents (two Witness, one MDK2) ran their suites at the same time with no collision. Pitfalls: a suite that never closes its games leaks 3.6 GB per run; `pkill -f <pattern>` kills your own shell when your command line contains the pattern (use `pgrep -f "[p]attern"`); an unquoted `eval` of exported Windows paths drops the backslashes.
- **Redirect the save folder from inside the mod, and test it by hashing the real one.** The game finds its save folder with `SHGetFolderPathW(CSIDL_APPDATA)`, so every copy and the owner's real game share one folder (a three-agent test wrote saves into it). Patch that import in the exe's import table from `DllMain` (memory patching only, the loader has already resolved the imports) and return a per-instance folder; read the setting lazily from the hook, not from `DllMain`. Verify by hashing the owner's real save folder before and after a full run: 76 files, every hash identical, while each instance wrote its own saves. From: The Witness.
- **Saves can load from the store's cloud API, not from the files you redirected.** Shadow of War writes its save to disk and through `ISteamRemoteStorage::FileWrite`, but loads it with `FileRead`, which `steam.exe` answers from the real Steam folder: every test copy loaded the same real cloud save while the redirected local saves were never read. Log the store's read calls once (pass-through wrappers on the same vtable slots) before trusting that a copy loads its own save, and serve the cloud from the copy's sandbox (`FileRead`, `FileExists`, `GetFileSize`, `GetFileTimestamp`, `GetFileCount`/`GetFileNameAndSize` from a folder; writes into it). From: Middle-earth: Shadow of War. Pitfall: a size match gave it away (the bytes read equalled the real cloud file, not the sandbox file).

## 3. Reverse engineering

- **Ghidra headless decompile-all.** Import the binary with `analyzeHeadless` and run a post-script that iterates every function, decompiles it and writes one big C file plus a TSV of addresses and names. Then a tiny wrapper that greps a function by regex. From: Deus Ex (a native DLL, 2,773 functions with C++ names preserved), FNV. Pitfall: run it in the background with a long timeout; keep the output in the project; names are only as good as the symbols in the binary. Do not install heavy MCP tooling that rewrites agent configs without asking.
- **REA (reverse-engineering agent MCP).** Registered per client with a setup command and needs a restart. Offered for FNV (NV:MP). Pitfall: registration was blocked for an agent and has to be run by the owner; plan a fallback (Ghidra headless).
- **Dump scripts straight from the package.** Unreal Engine 1 packages (`.u`) carry the original UnrealScript as text buffers; a small Python parser dumped 960 classes (about 120k lines) without the game's own compiler. From: Deus Ex. Pitfall: default properties are not in the dump; re-export with the game's tool once installed. The stock exporter asserts on a class with no script text, so do not rely on it to rebuild the package.
- **Scan archives for script text instead of parsing them.** In IW-engine zones (`.ff`) a script is a `name\0` followed by a zlib stream; inflate the zone and scan for that pattern. No asset parser, and the same 50 lines worked on 32-bit and 64-bit zones. From: MW2 (455 scripts from `common.ff`). Pitfall: a full zone parser written for one build broke on the next (pointer size changed in the 2026 64-bit update); the scanner did not care.
- **Archive format tools.** Write read, extract and pack tools for the game's archives and round-trip test them (pack, extract, `diff -r`). From: STALKER (`.db` archives: LZHUF index with a non-standard frequency limit, LZO1X data; addon is a plain tar). Pitfall: the textbook LZHUF constant corrupted output after about 97 KB; the game variant used a different maximum frequency.
- **Parse the data files for an oracle.** Parse the ESM plugin files into quests, stages, scripts and effects, then compare what should happen with what the game did. From: FNV (635 quests, 1,423 stages). Pitfall: the console did not accept editor IDs, only hex form IDs.
- **Runtime trace for "who did this".** When a body does something unexpected (a task set, a motion started), hook the engine's setters for animations and tasks, log the body, the value and the caller as module+RVA, and switch it on by INI so players can send the file too. Prefer this to more static decompiling: one short run named the code paths that set tasks and motions on mirrored NPCs. From: Gothic 3. Pitfall: keep it off by default and cap the file size; check each function's prologue bytes before patching so another build is refused.
- **Check whether "packed" code really is packed.** Denuvo and SteamStub on the exe do not always mean the game's code is hidden: compare each section in memory with the file (a probe reading pages while the game runs). In Shadow of War the 31 MB code section, the `.pdata` function table and `.sdata` were byte-identical; only Denuvo's own section was opaque, so the exe file could be disassembled directly (`dumpbin /disasm`, `.pdata` for function bounds) with no memory dump. From: Middle-earth: Shadow of War. Code Vein (UE 4.18, Denuvo): Denuvo had moved most function bodies into a large `.code` section and left a 5-byte `jmp` at each original address; the moved code is plain compiler output, and headless Ghidra decompiles a single function in about a minute without full analysis. The exe also has no ASLR, so the exec-thunk addresses in a UE4SS object dump can be hooked directly. An early "Denuvo, so static analysis will be slow" assumption, never tested, led to several detours; test one decompile first.
- **Let a release build describe itself.** Look for a console-variable/program registry and a compiled-in debug print. Shadow of War keeps a linked list of 680 named console programs and variables with descriptions, source files and line numbers (program handler pointers included), and a 12-byte debug-print stub with 1,100 call sites gated by one-byte channel flags. Catalogue the call sites statically (format string, category, guard flag), switch on only the channels you need, and hook the stub to log the game's own narration. From: Middle-earth: Shadow of War. Pitfall: other mods' fixed addresses may come from another build even when their byte patterns and data addresses match; verify every address against your build.
- **Signatures from the disassembly, verified live.** Build each signature from dumpbin output, wildcarding only rel32 call/jump targets and RIP-relative disp32 (recompute them from the printed target), and grow it until it matches exactly once in the code section; then check in the running game that it hits once at the same RVA and that the live bytes equal the file. From: Middle-earth: Shadow of War. Pitfall: dumpbin wraps long instructions onto a second line; a parser that misses it leaves displacements unwildcarded. A hand-written pattern for a tiny function matched twice because the compiler inlined a copy elsewhere; anchor such functions through a unique caller instead.
- **Static patch notes with signatures.** Record unique byte signatures for each target build so a patcher can refuse unknown versions. From: FNV (NV:MP signatures, one patch flipping a conditional jump). Pitfall: closed networking with no source means no quest sync can be assumed; confirm by reading, not by hoping.
- **Console handlers are the shortest path to the player.** A dev console's `Teleport`, `SetOrientation` and `Save` handlers are small and name exactly what co-op needs: where the player object hangs (`[[GameClient]+0x888]` in Shadow of War), the position and rotation fields (`+0xAC` float3, `+0xB8` quaternion) and what a save request does. Confirm the fields by moving the player with a virtual pad and reading them again. Before calling a handler from your own hook, read what it does to choose the thread: Shadow of War's `Player.Save` only arms a 0.5 s timer that the simulation thread checks, so the pad-reading thread was safe, although the game reads the pad on a different thread from its game logic. From: Middle-earth: Shadow of War. Pitfall: handlers that live in the DRM's protected section (`Player.GetPos` here) cannot be read; use their neighbours.

## 4. Building

- **Docker cross-compile when there is no local compiler.** An image with mingw (i686 or x64), cmake, ninja and ccache, named volumes for output and compiler cache, one script that takes an absolute worktree path and prints BUILD_OK or BUILD_FAILED. From: DK1. Pitfall: relative paths failed; the script needs absolute paths. A Docker Desktop WSL-integration popup is harmless if builds use Docker's own engine.
- **Native build gotchas.** An environment variable pointing CMake at the Android NDK toolchain made a Windows build target Android; unset it for the build. Package-manager dependencies compile from source the first time (long). Limit parallel compiles so the machine does not run out of memory. Compile a single file with MSBuild's selected-files option as a quick check. From: Ocarina of Time.
- **Keep the tree buildable at every save.** New source files are wired into the build in the same edit; a failed build must never leave a stale or deleted artifact (a failed Unreal make deleted the output package and the host then hung on a crash dialog). From: Deus Ex, FNV.
- **Shell scripting on Windows.** Bash heredocs and `python -c` mangle backslashes; write scripts to files. A `| tail` pipeline hides a failing exit code; use pipefail or check the exit code. From: FNV.
- **Load your code through a DLL the exe already imports from its own folder, and draw with a swap-chain hook.** The exe loads `AnselSDK64.dll` from its directory, so a proxy of it needs no injector. Export forwarders to the renamed original (`name = Real.name` in a `.def`) made the loader report "Real.dll was not found" even though the file sat next to the exe; make every export a small naked stub that calls `LoadLibraryW` on the full path on first use and jumps to the real function. Do no file or network I/O in `DllMain` (a log write to a `\\wsl.localhost` path under the loader lock hung the game); start a thread instead. For an overlay, create a dummy D3D11 device and swap chain, read `Present` from its vtable (index 8), overwrite that slot (swap chains of one implementation share the vtable) and draw from your hook. From: The Witness. Pitfall: the loader error is a Windows "System Error" box owned by `csrss.exe`, so the game process shows no window, 0 CPU and a few MB, which looks like a hang; it also stays on screen after the process is killed and appears in later screenshots. List top-level windows titled `<exe> - System Error`, close them with `WM_CLOSE`, and take a full-desktop screenshot when a launch stalls.
- **Calibrate a world-to-screen camera model against screenshots before building on it.** Read camera position and angles from the game, project a few known objects with `forward = (cos(pitch)cos(yaw), cos(pitch)sin(yaw), sin(pitch))`, and fit one focal length to two points on two axes; then draw markers from the hook and check them against a screenshot, at two headings and while walking. From: The Witness (vertical field of view 60 degrees, within a few pixels at 2405x1353). Pitfall: an engine's photo-mode callback (Ansel `updateCamera`) is only called in photo mode, so it does not give a per-frame camera.
- **A "frozen" game is often a modal error box; look for one before anything else.** Heat Signature under Proton seemed to stop after one or two frames, intermittently, for hours of debugging (ntsync, vsync, focus, overlay, Xalia and Steam restarts were all suspected). The real cause was the C runtime's `R6025 - pure virtual function call` box, a small visible window usually behind other windows, which runs a modal message loop on the game's main thread. Under Proton, list every window of the game (`xdotool search --class steam_app_<appid>` and `xdotool getwindowname` on each) and hook `MessageBoxA/W` in your DLL from day one to log the caller's stack. The R6025 came from the mod itself: it called the GameMaker runtime's instance variable getter (`vtable[1]`) through a pointer to a destroyed instance, whose destructor had reset the vtable to the base class's pure virtual stubs. Never keep raw instance pointers across frames without a liveness check (compare `inst->vtable` with the vtable of a known live instance). From: Heat Signature.

## 5. Fixing

- **Patch game scripts at load time instead of shipping them.** Replace the engine's script loader (MW2: `Scr_AddSourceBuffer`) so it applies small find-and-replace patches to the game's own script text as it loads, and check the patches offline against extracted scripts. The mod then ships its own code plus a few quoted lines, never whole game scripts. Log a hash of each changed script: in lockstep co-op both machines must compile the same text. From: MW2.
- **When a mod you build on can't be downloaded any more, ship it as a byte patch of the player's own exe.** Its installer usually holds a full copy of the game's exe, which you can't redistribute. Diff the installer's exe against the stock one (list it with 7-Zip, don't run it), ship the changed bytes with the stock bytes they replace, and have the patcher check size, SHA-256 and every original byte before writing a new file next to the stock exe (never over it). Check the table offline: applied to the stock exe it must give the installer's exe byte for byte. Also diff the copy the player has installed against the installer's: it may carry later changes by someone else (a resolution swap, blur off) that your mod silently depends on. From: Tony Hawk's Underground 2 (THEMOD 1.3, 122 bytes; the tester's copy had three more changes).
- **Make silent script errors loud.** Retail IW4 `Scr_Error` drops the message and only longjmps out of the failing script thread. A replacement that logs the last `va()` buffer and then longjmps exactly like the original (with the game's own `longjmp`) shows runtime errors. From: MW2.
- **Ship fixes as an add-on package, not a rebuilt original.** Subclass and swap: new classes extend the originals, a game-info subclass is selected by a config entry, and modules are mutators that receive forwarded hooks. Remap player classes at login to subclasses that share logic. From: Deus Ex (native layouts frozen because the DLL has no source; final/native functions cannot be overridden). Pitfall: if the original cannot be rebuilt, the only entry points are what the engine already lets you replace, so list them first.
- **Patch archives layered by name.** For archive-based games, append extra archives to the add-on and name test archives so they sort after the patch and override it. From: STALKER. Pitfall: the server checksums add-ons, so a leftover test file shows up as "different versions" for other players. Remove test archives and `cmp` the installed patch against the shipped one.
- **Host-authority state sync with a rules table.** One side runs the story scripts; others receive effects and apply them with local script execution suppressed. Rules (barrier, tether, controls, warp, rewards) live in data. From: FNV. Pitfall: duplicate rewards and ghost NPCs came from re-running scripts on guests; assert "no quest script ran on a non-host".
- **Make progress for the whole party explicit.** Decide, per piece of state, whether it is shared or per player (karma, reputation, rewards, hand contents, notes). From: FNV, DK1. Pitfall: undecided defaults caused the partner dropping what you held.
- **Fix the instrument first.** A wrong log (desync turn always 0), a capped FPS counter, a mode flag that silently fell back to single player: each produced "passes" that tested nothing.
- **Replacing a tiny leaf function: keep every register it keeps.** Callers built with whole-program optimisation may keep live values in *volatile* registers across a call to a function the compiler knows does not touch them. In Shadow of War a caller loaded `r9` before calling the 12-byte debug-print stub and passed it as `this` after it; the first hook (a normal C++ function reached by `mov rax,imm64; jmp rax`) clobbered `r9` and `rax`, and the game crashed on world load once a log channel was on. The same pattern shows at several other call sites (rdx, r9, r10 across a record-name getter and the debug print). Reach the replacement with a 5-byte `jmp rel32` to a page allocated within 2 GB (touches no register), save and restore rax, rcx, rdx, r8-r11, xmm0-5 and the flags, write only the stack slots the original writes, and register unwind info for the stub. Test it with generated code that loads known values into those registers and the caller's home slots, calls the hooked function and compares them after, plus a mutant that skips one restore. From: Middle-earth: Shadow of War. Pitfall: tests that call the hook from C++ never notice, because compiled callers do not rely on volatile registers.
- **A proxy DLL can end up loading itself.** Once the hook is staged as `bink2w64.dll` in the test copy, that file is no longer the original; passing it as "the original" to a test made the forwarders load a second copy of the proxy, which found its hooks already in place and stopped the process without logging (the first copy held the log file). Make tests reject a hook build given as the original. From: Middle-earth: Shadow of War.

## 6. Networking

- **Lockstep engines can hide state from scripts.** MW2's co-op mode runs the level scripts on both machines, and its script `getdvar` returns the real value only for dvars with certain flags (`SV_GetDvarCoop`), so both sides read the same. A dvar set from the console or by script read as empty, which silently disabled level start points and a QA scenario switch. Flag the dvars you need, identically on both machines, before the level loads. From: MW2.
- **Direct IP first.** Host and join by IP and port is the simplest thing that works over a VPN or port forward. From: DK1 (`-server`, `-connect IP:port`), Deus Ex, STALKER.
- **Steam "Spacewar" (AppID 480) relay.** Load the Steamworks flat API dynamically, use app 480, lobbies for invites and ISteamNetworkingMessages for relayed P2P, with manual callback dispatch. Needs a matching-architecture `steam_api` DLL and both players running Steam. From: DK1; see [networking-steam-spacewar.md](networking-steam-spacewar.md). Pitfall: "Join Game" with the mod not running launches Spacewar itself; tell the friend to start the mod first. Old DLLs bundled with games lack the flat API.
- **Mock `steam_api.dll` for local tests.** Export the same flat functions, fake Steam IDs from a nickname, carry messages over localhost UDP, fake lobbies and invites. Reproduce annoying real behavior (hold the first message from a stranger until the session is accepted). From: DK1. Pitfall: a lost one-shot packet exposed a harness race; make the mock resend instead of loosening the test. Then do one real-Steam smoke test and say honestly that the two-account join is unproven.
- **Packet loss and lag emulation.** Put a lossy, reordering, delaying link between simulated clients in game-free tests, and run a long soak (one hour, four clients converging). From: FNV sync core. Pitfall: lockstep games need to be tested with a deliberately slow side as well, since movies or loading screens longer than a timeout dropped connections.
- **Lockstep checksums as the oracle.** For lockstep engines every instance logs a per-turn checksum; pass only with zero mismatches. From: DK1.
- **Sync a state change as numbered, acknowledged effects, and gate everything on a stable world.** The side where a change happens detects it, sends it as an event with a sequence number inside a stream epoch, and resends it until acknowledged; the other side applies it once and in order, directly (a field write or a call to the game's own function), never by replaying the player's input. A restarted peer (new session id) starts a new epoch and gets the full state again; applying must be idempotent. From: The Witness (panel solved, door opened). Pitfalls found by running it: (1) a baseline taken while the world was still loading reported 39 transient "open" doors and the peer applied 30 of them; wait until the camera is valid and the entity counts are identical on three scans a few seconds apart, and queue remote events until then; counts alone were not enough (a default-open door powered up a few seconds after the gate and was sent as a player action), so also require the same set of solved or open items on every scan and fold changes in a short settling window after the gate into the baseline. (2) An echo guard that only marks the entity "known" fails when the game applies the change a moment later (24 echoes); suppress local changes to an entity for a few seconds after you apply a remote one. (3) Writing the fields a solve changed did not start the door; the opening came from a function call, so find the call (here the trainer's signature) and check the entity's type descriptor before calling it.
- **Keep responsibility for an acknowledged event until the game applies it.** A transport ACK can mean only "queued for the render thread". If the target entity is absent or a game call refuses the operation, retain the event and retry within a bounded queue; count it as applied and install its echo guard only after success. For independent monotonic state (solved panels, opened doors), let unrelated entities progress while one waits. Test by accepting and ACKing an event, making the adapter unavailable for longer than the echo interval, restoring it without another packet, and requiring convergence with no echo; a discard-on-failure twin must fail. From: The Witness, deterministic game-free adapter regressions (real-game transient failure not induced).
- **Test snapshot catch-up after the original deltas are acknowledged.** Solve something naturally on A, require both worlds to contain it, wait for A's events to be acknowledged, then restart only B into a fresh world. Keep A's PID and progress unchanged and compare the complete shared state read from both processes. A mutant that disables only full-state resend must leave the specific solved panel and its door missing on B. Otherwise a delayed original event or a resumed save can masquerade as successful catch-up. From: The Witness, targeted peer-restart scenario and mutant.
- **Separate engine IDs from table indices, and include slot zero in a census.** The Witness stores a base ID at `entity_manager+8` (observed 1); target resolution subtracts it before indexing the pointer array. A detector that starts scanning at 1 silently loses the door in slot 0. A natural second-puzzle bot caught the mismatch: both panels solved, second door open on only one machine. Keep the namespaces explicit in probes, confirm the lookup in disassembly, and retain a skip-zero mutant. From: The Witness, Tutorial Bend (`0x182` in the mod's table-index namespace).
- **Replicate activation separately from completion, and compare the target after a natural source action.** A solved panel can power another panel without solving it. The Witness needs a separate power-on event: detect requested power, call the native power-on method on the render thread, let the engine animate visible power, and give activation its own echo guard and snapshot entry. Assert both requested and visible power while requiring the target to remain unsolved; restart the recipient after ACKs and compare again. A disabled-power twin should preserve the source solve but leave only the target dark. Keep reversible power-off state out of a monotonic progression model until its authority policy is defined, and version the wire vocabulary when adding event kinds. From: The Witness, black/white tutorial panel `0x18AF` -> `0x1B`.

## 7. Testing

- **In-game bot.** Put the test driver inside the game: it writes the same packets or calls the same script functions a player would, then asserts the outcome and writes PASS or FAIL to its own log. From: DK1 (`-archontest*` flags), FNV (a JSON-RPC bridge plugin on a named pipe), Deus Ex (client driver class that runs real console commands so real RPCs are exercised), STALKER (a self-test script hooked from a restrictor). Pitfall: in STALKER the obvious hook (the actor binder update) never fired on the dedicated server; an effect on an always-online restrictor did. Find a hook that fires.
- **Live test harness with real clients.** One script launches a host plus N real clients, runs a named test with a timeout, prints `RESULT: PASS` or `RESULT: FAIL`, and a suite file lists the runs. From: Deus Ex (42 runs), FNV, DK1.
- **Mutation twins and negative controls.** Ship a deliberately broken variant with each feature and require its test to fail on it. Also self-check: two dumps of the same save must diff EQUAL, and a known change must be named exactly in the diff. From: FNV. Pitfall: a suite only counts as passed if its output proves tests ran; exit code 0 alone, or output like "is not recognized", is a failure.
- **Poll, do not check once.** Every assertion waits for a condition with a timeout. From: STALKER, Deus Ex (client probe answers arrive late under load). Pitfall: the one false FAIL was a check that ran before the flag arrived.
- **Three-way oracle.** Expected (parsed statically), captured (what the hooks recorded), observed (snapshot diff); classify every mismatch as oracle bug, capture gap, harness artifact or real bug. From: FNV.
- **Crash detection via log and dialog text.** Poll the log for `FATAL ERROR` and print the argument line; delete the log before each run so the next run does not inherit the last error. When a crash dialog hangs the process, capture its text with the window-text APIs, not a screenshot. From: STALKER boot test over all levels (found a missing model on three levels), Deus Ex.
- **Never desktop capture.** It records the owner's private apps. Use the game's own screenshot command or an in-engine capture and read those files. From: DK1, STALKER, FNV. Pitfall: a desktop recorder was used early in STALKER and had to be deprecated.
- **Census and measurement.** Periodic dump of object counts by kind, plus frame time rather than FPS. From: STALKER. Pitfall: a 60 FPS cap hid the real drops.
- **Write your own log file** if the engine log flushes rarely or only on clean exit. From: STALKER, Deus Ex (logs flush only on clean exit).
- **Drive a bot with real input and diff the shared state read from both processes.** Windows Python with `SendInput` (scancode keys, relative mouse moves, button down and up) after bringing the window to the foreground; aim from the camera angles with feedback (a measured radians-per-mouse-count), and read solved panels and open doors from both games' memory for the assertion, not from log lines. Add test-only config switches (drop the first send of every event, never resend, disable the echo guard) and keep a mutant that must fail for each. From: The Witness (4 scenarios: baseline, lost first send, and two mutants, all as expected). Pitfall: a long key press right after a window change was ignored once; press in short chunks and check the position moved.
- **Inject input inside the process so a bot needs no focus, and find the game's own gates by reading it.** For a game that drops input and throttles when its window is inactive: (1) hook the imports the game calls to learn what it uses (`GetRawInputData`, `PeekMessageA`, `Sleep`, `RegisterClassExA`; log each distinct call site and argument, and dump what a REAL event looks like, e.g. a real click made no raw record while mouse motion did); (2) disassemble the message pump and the handler for the message (`objdump -d`): the key and button handlers began with a check of one byte of an input-manager object, and the loop slept 100 ms on two other bytes; (3) hold those bytes from the `Present` hook and post the same messages the OS would; (4) because the game now believes it is active it will grab the real mouse, so virtualize the cursor calls (`ClipCursor`, `SetCursorPos`, `GetCursorPos`, `SetCapture`, `ShowCursor`) and test it by reading the system clip rectangle. Add commands for the bot's other needs (teleport by writing the player entity, a back-buffer screenshot) behind one command file. From: The Witness. Result: two bots ran at once beside another game with the owner's foreground, mouse and saves untouched (monitored, 1,648 samples). Pitfalls: a test that can pass without doing its work (two untouched games are identical): make the scenario assert the action happened; quote Windows paths in any shell command (an unquoted `C:\\x\\y` loses its backslashes).
- **Extract the sync logic into a pure library and fuzz it with bug twins.** Put the protocol (events, acks, epochs, gates) behind a `World` interface that reads and applies game state, keep the game adapter thin, and drive two instances with the hub's fuzzer over a lossy link and a fake world that has the real game's timing (loading, state that changes by itself after load, effects that follow an action by a fraction of a second). For every protection add a switch that turns it off (a twin) and require the fuzzer to fail it; a twin that is not caught means the profile never exercised that protection (for example, sessions shorter than the start-up gate). 500 sessions of 150 s run in 3 s. It found a restart flap, a start-up window that swallowed a real action, and a wrong field offset before any game ran. Sessions and epochs must grow with each start. From: The Witness.
- **Unattended menus through a virtual pad.** When the keyboard is Raw Input (posted key messages do nothing) but the game polls XInput, point the game's own `XInputGetState` import slot at a function that adds button presses to whatever a real pad reports, press on a schedule from when the game window appears, and stop on a line in the game's own log. Many games read pads even when unfocused, so no focus faking (which can make copies fight over the cursor) is needed. With a packed exe, find the slot in the rebuilt import table at run time by its value. From: Middle-earth: Shadow of War (title, campaign list and two more presses, in the world at ~48 s). Pitfall: the first log line after the campaign choice comes one screen before the world; stop on the world-start line.

## 8. Multi-agent

- **Sonnet worker agents.** Many cheaper worker agents for investigation and implementation, a main agent that coordinates and verifies. Always check the model setting when launching. From: all projects.
- **Investigate read-only, implement serially, then review.** One read-only agent per bug in parallel, one implementer at a time that builds and commits, a skeptical reviewer that repairs or reverts. From: Ocarina of Time. Pitfall: without a real build and no way to test two players, every fix is only reasoned from code; list what still needs a friend.
- **Isolated per-agent workspaces and ports.** Each agent gets its own test install pair, port, disposable workspace and (for engines with junctions) shared read-only data linked in. The run script only kills processes under its own root. From: DK1 (ports 5556, 5566, 5576), Deus Ex. Pitfall: shared state (files, ports, pipe names, the game slot) produced cross-talk; use OS-assigned ports and unique pipe names.
- **Two coding agents on one PC.** Each agent works in its own git worktree and branch, with its own pair of test copies, port, QA lock, run folder and stop script; `master` is the tested state. A step is merged after 3 passes plus a failing negative control, then the merging agent runs the full regression on its own pair before any package is built. Shared files (the protocol number) get small, early merges. From: Gothic 3. Pitfall: stopping an agent's background shell left the runner and both games alive and holding the lock; stop only your own pair with its script, never every process of the game's name.
- **Merge after green.** Lane agents do not commit; the coordinator commits after the full suite is green, and loosens a test only with a written reason. From: FNV. Pitfall: two agents both created a class with the same name; rename on merge.
- **Verify agent claims.** One agent said the host could not use computers; a test showed it could. Another's audit finding needed checking before fixing. From: Deus Ex.
- **Respect the safety layer.** When a classifier blocked a bulk scrape or a cross-process handle close, the right move was to stop, explain, and hand the action to the owner or choose an in-process alternative. From: STALKER, FNV.
