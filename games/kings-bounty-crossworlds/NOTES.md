# King's Bounty: Crossworlds research notes

Status: research in progress. Static inspection was done on an isolated copy of the owner's Steam install; the original install and saves were not modified. No mod was installed or run. No game files or assets are included here.

## Observations

- Steam identifies App 63910 as King's Bounty: Crossworlds, released 2010-09-17. The store page lists Single-player and describes the Armored Princess campaign plus the Champion of the Arena and Defender of the Crown mini-campaigns. Source: https://store.steampowered.com/app/63910/
- Co-op Anything's current `DIRECTORY.md` and `games/` folder have no King's Bounty / Crossworlds entry.
- The inspected Steam installation's manifest reports build ID `7254336`. The executable has no FileVersion or ProductVersion string; treat the manifest ID as a Steam depot build identifier, not as the in-game version. The exact executable identity is recorded privately in ignored `local/identity.md`.
- Static PE import inspection of that `kb.exe` found Winsock imports for initialization/cleanup and TCP socket operations, including `socket`, `bind`, `listen`, `accept`, `connect`, `send`, `recv`, and `select` (several are imported by ordinal). A direct x86 call-site scan found calls to multiple imported socket functions, including socket creation, bind/listen/accept, connect and send. The binary also registers Lua globals `NetListen`, `NetSend`, `NetConnect`, and `NetConnected`, and contains engine client/server classes (`serv_server_tcp_c`, `serv_client_tcp_c`, `ModuleLogicServer_c`) and game-logic commands (`SPAWN_CLIENT`, `cmd_server_addclient_c`). The inspected `data/app.ini` sets `~debug_server` to `TCP:0.0.0.0:51515`; a GOG forum post shows the same setting in a Crossworlds app.ini. This points to a debug service as one likely consumer of the TCP layer, not a user-facing multiplayer mode. No remote listener was started or port exposed. Sources: https://www.gog.com/forum/kings_bounty_series/cant_install_update_for_crossworlds_goty/post2 and https://learn.microsoft.com/en-us/windows/win32/winsock/winsock-functions
- Static disassembly of the Lua registration block mapped the four `Net*` globals to native wrappers: `NetListen` accepts one string and starts/replaces a TCP endpoint object; `NetConnect` accepts one string and creates a separate endpoint object; `NetSend` accepts one string and passes it to the listener wrapper's send-buffer handler; `NetConnected` reads the listener wrapper's status flag. The endpoint parser explicitly compares the address scheme to `TCP:`. This Lua table exposes no receive function or message callback. These are API-shape findings only: inbound handling may exist below Lua, and the debug protocol or any relationship to game-session state remains unknown.
- Further static cross-reference checks found the `debug_server` string in a generic configuration-descriptor registration routine, while the Lua `Net*` globals are registered in a separate block. This string xref does not establish that `debug_server` invokes `NetListen` or that the configured service accepts game clients. The same Lua module registration maps names `initserver` and `server` to native functions, but their presence and names alone do not show player joining or campaign replication. No runtime listener or network client was started.
- Targeted Ghidra decompilation on the recorded Steam build found a native TCP path below the Lua wrappers: the server routine calls `socket`, `bind`, `listen` (backlog 5), and `accept`, then wraps accepted sockets; the client routine calls `socket` and `connect`; separate server/client methods loop over `send`; and a stream reader calls `select` and `recv` into a buffer. This confirms bidirectional native transport, correcting any reading of the missing Lua `NetReceive` export as proof that the binary cannot receive data. The receive-to-Lua/game-command path, wire format, and relation to campaign state remain unknown. The Ghidra full-file auto-analysis hit its 300-second timeout; these findings came from targeted decompilation of the identified functions, not a runtime test.
- Follow-up decompilation traced more of that path: the TCP receive routine appends received bytes to a growable per-connection buffer; on a newly accepted socket, a worker calls a virtual method at offset `+8` on the owning server object and then performs cleanup. The client-side receiver likewise enters through a virtual method on its owner before the read loop. This shows the socket wrapper hands connection/read lifecycle to engine methods, but the callback target, message framing, Lua delivery, and game-command dispatch are not yet identified. A nearby function that initially looked like queue insertion is actually a growable-array insertion of a connection object; its consumer and relationship to `ModuleLogicServer_c` remain unknown. These are static decompilation observations, not runtime findings.
- The accepted-server wrapper's vtable resolves that virtual `+8` call to a method that checks the listening socket with `select`; it is a connection-readiness/status probe, not evidence of campaign replication. The outgoing-client vtable has separate methods for `send`, connection status and receive-thread handling. A byte-append helper grows an internal buffer in 0x400-byte increments. The framing parser and use of these buffered bytes are still unknown.
- Hook-point test: PE import parsing confirms `kb.exe` imports only `DirectInput8Create` from `DINPUT8.dll`. A small x86 Rust proxy was built privately and loaded from the isolated test copy; it resolved and forwarded to the Windows `dinput8.dll`, and the game process remained alive for the 15-second smoke window. Before launch, the test copy's `debug_server` setting was restricted to loopback; its `app.ini` was restored byte-for-byte afterwards. This verifies only DLL loading/forwarding, not a Lua hook or co-op. The temporary proxy DLL and its log remain in the ignored test copy because the environment rejected the cleanup command; they are outside the original install, and the test process was stopped.
- Static trace of the Lua `Net*` registration: a registration routine at `0x5d2c20` builds name/function pairs, including `NetListen`, `NetSend`, `NetConnect`, and `NetConnected`; it passes them through a generic registration wrapper at `0x6999a0`, which delegates to a lower-level helper at `0x81d950`. This gives a candidate extension point for adding a receive bridge, but the VM state access, Lua version/API details, safe main-thread scheduling, and runtime call timing still need to be confirmed before hooking it.
- The same-engine comparison lead is stronger but still indirect: a contemporary Elven Legacy preview describes LAN, Internet and hot-seat play, and PCGamingWiki documents direct-IP multiplayer for Fantasy Wars. Both use TheEngine. No multiplayer executable, session archive or packet capture from either game has yet been compared with Crossworlds, so protocol and code reuse remain unknown. Sources: https://forumcontent.paradoxplaza.com/public/14648/PARADOX_DPAD10.pdf and https://www.pcgamingwiki.com/wiki/Fantasy_Wars
- The native Lua `Logic` registration table maps `hero_lu_var`, `hero_lu_item`, `hero_lu_army`, `cur_lu_army`, and `src_lu_army` to game functions. Static decompilation of `hero_lu_army` shows it resolves the active game context's current hero before applying the army string; its Lua wrapper accepts only that string, not a hero/client identifier. The helper that resolves the current hero consults active global/current-object state. This is evidence that the exposed scripting API is centered on the currently selected hero, not evidence that the engine cannot represent a second hero through a lower-level object API. Static analysis only; no second hero has been spawned or controlled.
- The scenario-action table maps `SPAWN_CLIENT` to a native action object. Static decompilation of its execute method shows it calls the engine's object factory, whose type table contains `static`, `dynamic`, `hero`, `army`, `box`, `castle`, and `npc`. The editor's action descriptor labels its inputs `Template logic unit`, `client's atom`, animation/blend, spawn angle/scale, and logic-unit variables, confirming it is a generic scenario actor-spawn action. The `hero` factory installs the RTTI-identified `atom_hero_c` vtable. When the template has no hero-state pointer, that factory calls the constructor whose vtable is RTTI-identified as `client_hero_c`, then links that new state object back to the atom; otherwise it links the supplied state object. The `client_hero_c` hierarchy includes `client_automoved_c` and per-instance methods that read/write its own position and movement state. This is a native path to an atom backed by a separately allocated client-hero state, making it a plausible basis for a second independently progressing hero. Independent user input, active-hero selection, UI binding, army ownership, save/load behavior, and network synchronization remain unproven. A bounded scan of text-like stock session scripts found no use of `SPAWN_CLIENT`; the action has not been invoked at runtime.
- The public [KBSE source repository](https://github.com/neptunehs/KBSE) documents a `version.dll` plugin framework with a Lua C-function bridge and game event hooks. Its source is pinned locally for private analysis at commit `1534747940bd0b9b9ac29a625501bbe38400f663`; the GitHub repository has no license file. Its published compatibility statement is Steam 1.3.1 English build 6171, while this owner has a Russian installation and only the Steam manifest build ID is established. Some documented registration addresses match functions independently found in this build, but this does not establish full compatibility. The project README calls itself AI-generated; its docs also contain conflicting descriptions of the VM, so validate claims against the binary before reuse. No KBSE files were installed or copied into the project.
- Co-op implementation decision is still open. Do not select lockstep or assume the native TCP layer replicates the campaign: first identify how the engine callback frames incoming messages and how a multiplayer session maps accepted peers to game clients. The eventual target is a host-authoritative shared campaign with independently running game clients; the one-copy Parsec workaround is only a temporary shared-control fallback.
- Loopback-only startup smoke check on the isolated test copy: backed up `data/app.ini`, changed only `~debug_server` to `TCP:127.0.0.1:51515`, and launched `kb.exe` hidden. No listener on port 51515 was observed during the 30-second window; the process remained running. The original config was restored and its SHA-256 matched the backup. This does not rule out a listener that starts after a game session or menu action; no external interface was bound or probed.
- The quick search across text-like `.lua`, `.lu`, and `.script` entries in the installed `.kfs` archives found no network/multiplayer terms. It did find Lua scripts in `sessions/addon/ses.kfs` (221), `sessions/orcs/orcs.kfs` (63), `sessions/champion/champion.kfs` (30), and `sessions/defender/defender.kfs` (17). This is a bounded token search, not a full script/API analysis.
- The install contains `LuaIDE.dll`, and the session archives are ZIP-readable `.kfs` containers. No archives were modified or extracted into the public repository.
- The Nexus listing for nPwka Engine Extension describes a DLL extension with a Hardcore mode, online leaderboard, reserve slots, speed controls, screenshot changes and Lua/modder additions. It does not advertise co-op or player/state synchronization. It requires Crossworlds 1.3.1 (build 6171), supports English and Russian builds, and says public mods depending on or building on its features require the author's permission; private development/testing is allowed. Source: https://www.nexusmods.com/kingsbountycrossworlds/mods/38
- ModDB lists multiple Crossworlds content/mod projects but no co-op project surfaced in its mods listing. Bounded search only. Source: https://www.moddb.com/games/kings-bounty-crossworlds/mods
- TheEngine is identified as the engine for both Fantasy Wars and Elven Legacy. PCGamingWiki lists multiplayer for Fantasy Wars and lists LAN and hot-seat play for Elven Legacy; the latter's official internet service is shut down. Neither source establishes co-op campaign support in Crossworlds. Sources: https://www.pcgamingwiki.com/wiki/Fantasy_Wars and https://www.pcgamingwiki.com/wiki/Elven_Legacy_Collection
- A contemporary Elven Legacy preview reports that its multiplayer included LAN, Internet and hot-seat, and allowed custom multiplayer maps. This is an adjacent-engine research lead, not a claim that its multiplayer was co-op or that its code can be reused directly. Source: https://forumcontent.paradoxplaza.com/public/14648/PARADOX_DPAD10.pdf

## Derived

- No ready-to-use Crossworlds co-op solution surfaced in the searches listed below. The executable has a Lua-facing TCP API and a native TCP receive path, but its configured endpoint is explicitly named `debug_server`. This may be useful as a transport only after its receiver/callback semantics and relationship to the game session are traced; native socket operations alone do not prove campaign replication.
- The `debug_server` literal's direct cross-reference is to generic configuration registration, not directly to a socket or Lua wrapper call. Its runtime consumer remains unknown; the `debug_server` name and `TCP:` value make a debug service plausible, but do not prove the exact behavior.
- The same-engine multiplayer games provide a practical comparison target for their client/server startup, state replication and network setup. Their multiplayer modes are not evidence that Crossworlds includes a playable multiplayer menu or shared campaign.
- The game is a real-time overworld plus turn-based tactical battles; any campaign co-op design must decide turn/control ownership and synchronize hero, battle, quest, inventory, and save state. This is design analysis, not an implementation finding.
- nPwka Engine Extension may help explain the native hook and script-extension surface, but its published features are not multiplayer. Respect the author's public derivative/dependency restrictions.
