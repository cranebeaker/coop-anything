- **Fullscreen was the problem.** With those settings the game ran an exclusive 2560x1440 device; when it lost the foreground the window was minimised to 160x28 (screenshots 160x28 and 80x14) and nothing moved (observed). The saved video settings only match fullscreen mode entries (`mode+0x10c != 0`; windowed entries are built with `+0x10c = 0` in the startup mode list code near decompile line 313276), so the registry cannot select windowed.
- **Windowed fix (`src/window.c`, `OBSCOOP_WINDOWED=1`):** hooks `d3d9!Direct3DCreate9`, then `IDirect3D9::CreateDevice` (vtable slot 16) and `IDirect3DDevice9::Reset` (slot 16): sets `Windowed = TRUE`, refresh rate 0, gives the window a caption and the client size of the back buffer, and restores it if it was minimised. Result (observed): 806x629 captioned window for the default 800x600 mode, style `0x14ca0000`.
- **Pitfall (observed, run 6):** `Direct3DCreate9` is called twice and both devices share one vtable. Patching a slot that already held our hook stored our own hook as the "original", so `CreateDevice` called itself until the stack overflowed (2.5 MB of log, the game exited). Fix: skip a slot that already holds the hook. Same rule applies to `Reset`.
- **Pitfall:** the launcher quoted `$env:OBSCOOP_WINDOWED` without the backslash, so bash swallowed it and the game stayed fullscreen. Check `window: fullscreen ... -> window` in `obscoop.log`.
- **Result (observed, `move_test.py`, windowed unfocused / minimised / restored):** the game keeps simulating and reading virtual input in all three states, with the same numbers.   - **3** load by name: `FUN_004a1bd0(name)` copies a string to `game+0x324`; the handler runs `(*(game+0x318))->vtable[1]`, then retags the `CHC2` entry of the character table at `*(game+0x318)+0x1b18` as `CHTM` (player 2 becomes a teammate again, derived), clears `+0x464`, takes the level from `+0x1c4c`,
  - **4 change level**: `FUN_004a1c00(level, entry, flag)` sets `game+0x364` = level tag, `+0x368` = entry (door) id, `+0x370` = flag, then `+0x320 = 4`. The `Cslh_ChangeLevel` script command calls exactly this (vtable slot 4, `0x4bf6d0`) with the three script arguments. The handler (`FUN_004a3c10(level)` loads it, `FUN_004a1fc0`) then finds the door entity whose tag is `HRDD`/`ODOD` and whose id equals `+0x368` and puts the characters there,
  - **9** back to the menu: sets `game+0x310 = 4`.
  - `game+0x310`: game mode, 1 in game, 4 menu (observed live: 1).
- **Level tags** are 4 ASCII characters (observed live: level `B101`, stored as dword `0x42313031`, read as "101B" in little-endian text). The same tag sits at `game+0x364`, `world+4` and `*(game+0x318 / 0x31c)+0x1c4c`. The handler compares tags such as `0x4a303036` ("600J"), `0x49303032`, `0x49303031`.
- **Two progress objects:** `game+0x318` and `game+0x31c` point to two objects of the same layout (identical at the start of the game; presumably the live progress and a saved copy: derived). Each has the current level tag at `+0x1c4c` and a table of **8 per-character records** at `+0x1b18`, stride `0x28`: `+0` controller tag (`CHC1`, `CHC2`, `CHTM`, or 0), `+4` float 100.0 (health, derived), `+0x1c` character tag (BOY2, BOY3, BOY4, GIR1 to GIR4 in order), `+0x20` that character's level tag, `+0x24` an id. In the live read the controller tags are `1CHC` at slot 1 and `MTHC` (CHTM) at slot 5: it looks one slot off from the character tags, so the field meanings are not settled.
- **Managers:** `world+0x175c` human manager (count `+4`, capacity `+8`, array `+0xc`, vtable slot 1 frees them all, slot 2 allocates a capacity); `world+0x1760` is the `CCharacterNPCManager` (constructor `FUN_004f3550`, size 0x1b4, same container layout, it holds the NPCs and enemies: to read next).
- Scripts: `FUN_004a1c40` (`%sCharacters\%s\%s.dat`) loads a character data file by name.

### Runs 33 to 35 (2026-10-25): story state, joining a game in progress, inventory (partly mapped)
**Progress object (observed, `prog_dump.py`):** `game+0x318` is the **live** progress object (it changes on a level change); `game+0x31c` is a saved copy that stays as it was (identical at game start). Layout (offsets in the object):
- `+0x000` vtable `0x66b320`, `+0x004` the tag `GAME`; `+0x810` a pointer (never copy it).

### Runs 36 and 37 (2026-10-26): an idle player 2 walking by itself - found and fixed (test build 0.7)
- **Reproduced without any network:** one copy, fresh "New game, Two players", both virtual pads connected (`OBSCOOP_VPADS=0,1`), player 2's pad untouched. Holding player 1's stick makes player 2 move 60 to 200 units on its own: it starts about 2 s after player 1 and moves in the same camera-relative direction. With player 1 idle, player 2 stays put. The same happens on both copies of a linked pair, so it is the game's local co-op behaviour, not a sync artefact.
- **Cause (decompile, then confirmed live):** the character update `FUN_004de4f0` sets two per-frame flags on every human, `+0x880` ("off-screen in view 0") and `+0x884` ("off-screen in view 1"), and clears each one when the character projects inside that view. The input update `FUN_004cf940` (thiscall, ECX = the `CCharacterControllerInput`, one `delta ms` argument) then checks, for a character that is not the camera target, `+0x884`: if set, it starts a catch-up to the camera character at speed 200 and sets its own `+0x1d5` latch; while `+0x880` is set, it skips the normal pad handling. This is the shared-screen local-co-op leash that brings a companion back on screen. With one camera per player it fires constantly, so the remote player's character walks itself.
- **Fix (`src/hooks.c`, build 0.7):** hook `FUN_004cf940` (prologue `55 8b ec 83 ec 3c`, 6 bytes) and zero `character+0x880` and `+0x884` just before calling the original. The character update recomputes the flags every frame, so this only changes the input decision. The hook installs on both host and guest (`hook: CharacterControllerInput update (0x4cf940) hooked` in both logs).
- **Measured with the hook (`verify_keepalive.py`, two copies, UDP loopback):** player 1 walks 267.7 with the guest pad untouched: player 2 moves **0.0** on both copies, P2 drift 0.0 (before: 64 to 200 units). The guest pad moves player 2 by 112.0/111.9 while player 1 stays at 0.0; both walking: P1 267.8/267.9, P2 54.6/54.9. With the lag relays (`duo_lag.py 60 20 1`, 60 ms + 0..20 ms each way, 1% loss): P1 walks 268, P2 0.0, P2 drift 0.0. The door in that lag run did not open (no level change), so door timing under lag is not covered by tests.
- **Discarded first attempt:** feeding the idle pad a small stick value (8000 or 9000, above XInput's 7849 activity threshold and below the movement deadzone) suppressed the catch-up on a single copy but not on a linked pair, so it was removed. Writing 0 to `+0x880` alone, to the 2 s character timer `+0x6f8`, or to `+0x7ac` did not stop the walk.
- Test build 0.7: 0.6 plus the catch-up hook (DLL SHA-256 `87c55932836e54cef20f35fe09adfe00b18a24d6bb9d23d5ec853bb74c5a93d3`); the packet protocol is still 3, so 0.6 and 0.7 connect, but a mixed pair (one 0.6) still shows the self-walk on the 0.6 copy.
